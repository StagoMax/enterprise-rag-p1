## 先建立一张全景图

```text
原始文档
  └─ 分块（旧字符块，或结构化的 child/parent）
       └─ 多路召回：dense + 正文 BM25 + 标题 BM25 + 特征 BM25
            └─ RRF 合并候选 → 按 document_id 聚合为 20 份不同文档
                 └─ 补齐命中 child 的 parent 章节 → LLM 重排（可选）
                      └─ Top-3 文档 → 摘录器压缩证据 → 回答与引用

关系/多跳问题额外走：
Hybrid 种子文档 → ACL 裁剪后的显式引用图（最多两跳）
                → 图目标文档的受限检索 → 与基础候选一起返回
```

这里有三个常被混为一谈的对象：

- **chunk（块）**：检索和嵌入的最小单元；一篇文档有多个 chunk。
- **document（文档）**：用户最终看到和评测的引用单位。重排时比较的是不同文档，不是 20 个可能来自同一篇文档的 chunk。
- **parent（父章节）**：结构化分块中，一个或多个 child 所属的较完整章节；它不是“父文档”，仍然属于同一篇文档。

## 1. 各阶段的分块策略及其原理

### 1.1 为什么必须分块

技术支持文档经常同时包含症状、环境、原因、解决步骤、版本、长日志和参考链接。把整篇文档只做一个向量，语义会被平均，问题和答案之间的关键局部关系会变弱；切得太小，又会把“原因 + 操作步骤”拆散。因此分块本质上是在两个目标之间取平衡：

1. **小而聚焦**，便于 dense/BM25 找到与问题最相近的证据；
2. **大而完整**，便于重排器和最终回答理解条件、因果和步骤。

### 1.2 阶段与策略

| 阶段/索引 | 参数与单位 | 做法 | 主要目的与代价 |
|---|---|---|---|
| P1/P2 的早期实现 | 报告未固化单独的参数快照 | 段落优先的传统窗口分块 | 先跑通检索、ACL、引用和 Graph 闭环；不要把后来代码默认值倒推成 P1/P2 的严格实验参数。 |
| P3 历史基线 `legacy-characters-v1` | `900` 字符，重叠 `100` 字符；147,358 chunks | 先按空行/段落累积；超长段落用滑动窗口，后一块带上前一块末尾 100 个字符 | 逻辑简单，重叠降低“答案恰好跨边界”漏召；但字符不是模型 token，窗口可能跨越语义章节，且没有完整上文。 |
| 结构化父子 v1 | child `384` tokens，overlap `64`；parent 最大 `1,200` tokens | 识别 Markdown/编号标题和 `QUESTION`、`CAUSE`、`ANSWER`、`RESOLVING THE PROBLEM` 等章节；短章节合并为 parent，再切 child | child 保持检索颗粒度，parent 保留章节因果。384/64 全量为 82,228 个 child、32,219 个 parent。 |
| 结构化参数消融 | child `320/48`、`256/48`，parent 均 `1,200` | 只改变 child 大小/重叠，其他候选契约、语料和重排模型保持一致 | 更小块通常改善 Top-20 候选覆盖，却可能让单块上下文更碎；最终要和重排模型联合选择。256/48 在 Sol 的历史 55 题上取得最佳综合结果，但不是所有模型的绝对最优。 |

`900/100` 的单位是**字符**，`384/64` 等单位是项目的近似 **token**。二者不能用“384 比 900 小很多”直接比较；英文、中文、URL、错误码被计数的方式不同。

### 1.3 旧字符窗口如何工作

假设一段文档为：

```text
[第 1 块前 900 字符]
                    [后 100 字符重叠 + 第 2 块的新内容]
```

重叠让“故障现象在块尾、解决动作在块首”的问题仍有机会在任一块中同时命中。它的缺点是重叠内容会重复入库，且分割点只大致尊重段落，未必尊重 `CAUSE → ANSWER` 这样的技术结构。

### 1.4 结构化父子块如何工作

结构化策略先形成标题路径，例如：

```text
Document
└─ RESOLVING THE PROBLEM                         ← parent，最多 1,200 tokens
   ├─ Section: ... + 原因与前半步骤              ← child 1，最多 384 tokens
   ├─ Section: ... + 末尾 64 tokens + 后续步骤   ← child 2，最多 384 tokens
   └─ ...
```

- **child** 的标题会重复在块内，因此“答案”或“原因”等章节语义也会进入向量和 BM25；它用于快速召回。
- **parent** 可以由相邻短章节组成，但严格不超过 1,200 tokens；它用于给人或模型补全局部块缺失的前因后果。
- child 的 64-token overlap 只在一段确实需要拆开时使用，避免拆断长段落。

所以父子分块不是把文档复制成两套同等索引：主要检索的是 child；parent 是同一 child 的可追溯上下文。

## 2. “父块在重排前补齐”是什么意思

### 2.1 修复前：完整证据来得太晚

初版结构化流程是：

```text
child 检索 → 用 child 重排 → 选出 Top-3 → 再取 parent 给回答
```

这使 parent 只能改善最终回答文本，**不能改变哪三份文档胜出**。而 LLM 重排器每份文档的输入还有约 680–700 字符预算；它实际比较的是被截短的 child，而不是“原因 + 解决步骤”完整章节。结果是结构化分块把 Gold 放入 Top-20 的能力提高了，却有更多候选没有被排进 Top-3。

### 2.2 修复后：让排序器看到相同层级的证据

现行逻辑是：

```text
1. child 多路召回
2. 按 document_id 聚合出 20 份不同文档，每份保留少量最相关 child
3. 根据这些 child 的 parent_id，批量、去重补齐 parent 内容
4. 从 parent 中按问题提取受预算限制的重点片段
5. LLM 比较 20 份“文档级证据”，给出顺序
6. 取 Top-3，再由摘录器为回答压缩证据
```

“补齐”不是向候选集中新增其他文档，也不是无上限拼接全文；它只是把**已召回 child 的原 parent 章节**拿回来，且同一 `parent_id` 只取一次。修复后，结构化 + DeepSeek 的历史 Recall@3 从 `44/55` 回到 `46/55`，说明一些本已进入候选池的正确文档终于有了足够上下文被模型识别。

## 3. 独立 collection、索引版本与 alias 切换

### 3.1 是否要把所有文档复制一次？

要区分“原始语料”与“检索索引”：

- 原始 `documents.jsonl` 可以只有一份，不因新索引版本而复制一份源文件。
- **发布完成后，每个 Milvus collection 都是一份可独立查询的完整索引快照**：其中包含该版本全部 chunk 的正文/元数据、dense 向量、BM25 字段、ACL 字段和 parent 字段。因此从向量库磁盘占用看，各版本之间确实存在完整数据副本，不是只保存差异。
- 但“完整快照”不等于“每次都把所有原始文档重新解析、分块和嵌入”。常规 `commit()` 会把旧 collection 中**未变化文档的现成行和向量**批量复制到新 collection，只对新增或变更文档重新分块、嵌入和写入。
- 离线全量建库或分块/向量契约发生变化时，旧行已不兼容，才会遍历全部源文档并重建全部向量；断点续建则把完整文档批次直接追加到尚未发布的 collection。

这是有意的快照式发布取舍：多占一段时间和空间，换来在线查询永远看到一个完整、一致的版本，而不是“旧块 + 新块 + 半更新 ACL”混在一起。当前工程没有实现跨 collection 的物理去重或共享底层向量；旧 collection 的保留/清理应由版本保留策略控制。

```text
源文档：只保存一份

collection v1：A旧向量 + B旧向量 + C旧向量      ← 完整快照
collection v2：A旧向量 + B新向量 + C旧向量      ← 仍是完整快照
                       ↑
                 只有 B 重新嵌入；A/C 的旧行直接复制
```

### 3.2 怎么切换，为什么不会中间态

collection 的实际命名是类似：

```text
enterprise_chunks__p3_techqa_28481_nemotron_1024_fielded_v1
                         ↑ 未发布的完整候选版本

enterprise_chunks       ↑ 在线查询固定使用的 alias
```

发布顺序：

1. 创建没有 alias 的新 collection；
2. 按完整文档批次切块、嵌入、写入。中断后只在**未发布** collection 按 `document_id` 续传；
3. 发布前比较 collection 中的文档 ID 集合与本次源语料集合，必须完全相等；
4. flush、load 完成后，用 Milvus `alter_alias` 将 `enterprise_chunks` 一次性指向新 collection；
5. 查询始终只访问 alias，因此下一个请求要么命中旧快照，要么命中新快照，不会读到半建好的版本。

回滚也是把同一个 alias 改回已验证的旧 collection，不搬迁数据。Graph 关系快照要与检索版本成对发布/回滚，避免新文档索引配旧关系边或反过来的“跨版本路径”。

### 3.3 “不同索引版本”到底可能不同什么

即使源文档 ID 相同，以下任一项变化都应产生新索引版本：

| 变化维度 | 例子 | 为什么不能和旧块混用 |
|---|---|---|
| 源内容或文档版本 | 文档更新、撤权、状态变更 | 证据和 ACL 必须对应同一快照。 |
| 解析与分块契约 | `900/100` 改为 `structured 256/48 + parent 1200` | `chunk_id`、正文边界、parent 关系和召回单位都变了。 |
| 向量契约 | 嵌入模型、维度、归一化/前缀 | 向量空间不兼容，旧向量不能和新向量直接比较。 |
| 检索 schema | 新增 `title_sparse`、`feature_sparse`、`roles_key` | 查询分支需要对应字段，ACL 过滤也依赖正确字段。 |
| 图快照 | 显式引用边的新增、删除、版本关系变化 | 路径必须只经过与当前文档快照一致且已授权的边。 |

查询期参数（例如 dense 权重、是否启用 LLM 重排）也会影响结果，但它们不一定都要求重建 collection；应与索引版本一起记录，才可复现实验。

## 4. Graph 专项的三个 100% 指标与 `+32.5 pp`

这些是 **40 道 `graph_rag` 专项题**的指标，不是普通 RAG 的 40 道随机题。每题的 Gold 明确写出了种子文档、目标文档和应返回的路径。例如：

```text
期望路径：isg3T1024513 --REFERENCES--> swg21294023
期望来源集合：{isg3T1024513, swg21294023}
期望图目标：swg21294023
```

| 指标 | 一道题算对的条件 | 100% 表示什么 |
|---|---|---|
| Graph 联合 Recall@3 | Top-3 同时包含 Gold 的**全部**期望来源；本专项通常即种子和目标都在 | 40/40 都同时找回了起点与关系目标。 |
| Graph 目标 Recall@3 | Top-3 至少包含 `expected_graph_target_ids` 中的目标 | 40/40 都找到了最终要追踪的关联文档。 |
| Graph 路径准确率 | 响应的 `graph_paths` 中至少有一条 `node_ids` 与 Gold 的完整节点序列一致 | 40/40 都不仅“碰巧找对目标”，还报告了被题目要求的可审计路径。 |

`+32.5 pp` 中的 `pp` 是 **百分点（percentage points）**，不是“提升 32.5%”。P3 的计算是：

```text
Graph 目标 Recall@3       = 100.0% = 40/40
同一专项、强制纯 Hybrid    =  67.5% = 27/40
绝对差                    = +32.5 个百分点
```

P2 时纯 Hybrid 目标 Recall 只有 `17.5%`，所以增益为 `+82.5 pp`。P3 扩到全量语料后，普通 Hybrid 更容易直接搜到目标，因此 Graph 的**边际增益**降了；Graph 的专项成功率并没有从 100% 下降。

## 5. 种子、图证据和完整路径

| 名词 | 本项目中的含义 | 作用 |
|---|---|---|
| 种子（seed） | Hybrid 先检到的前 2 个不同文档 | 作为图遍历起点；Graph 不是无约束地从全图游走。 |
| 图证据 | 从种子沿显式 `REFERENCES` 边到达的目标文档，且目标文档又通过 ACL + candidate-restricted 检索取回相关正文 | 证明“这份目标文档不是模型编的关联”，同时提供可回答的实际文本。 |
| 完整路径（full path） | 节点序列、关系类型、路径置信度；如 `A --references--> B --references--> C` | 用来审计“为什么引入 C”，也用于 Graph 路径准确率评测。 |

执行中先算出当前角色可见的 document ID 集，再构造授权子图；不可见节点不会进入队列、路径、引用或答案。遍历最多两跳、最多 12 条路径，并避免环。到达的图目标也不是直接塞给回答，而是在只允许这些目标 document ID 的候选集合内再次做检索，找到与原问题最相关的 chunk。

## 6. “有界正向特征，不做硬过滤”

问题中出现的产品、组件、错误码、版本号通常是非常强的线索，例如 `WebSphere`、`DB2`、`SQLCODE=-1585`、`8.5.5.3`。系统会从问题和候选文档抽取这些特征，计算覆盖率后添加一个**只会增加、且封顶**的分数：

```text
boost = 0.08 × 产品覆盖率
      + 0.05 × 组件覆盖率
      + 0.12 × 标识符/错误码覆盖率
      + 0.04 × 版本覆盖率
boost ≤ 0.20
```

这就是：

- **正向**：匹配时加分；不匹配只是不加分，不扣分。
- **有界**：最多加 `0.20`，不会让一个错误码词面命中压倒全文语义和标题证据。
- **不是硬过滤**：不会写成“候选必须包含相同版本/产品，否则直接删除”。

例如问题同时出现 `WebSphere`、`MQ`、错误码 `2035` 和版本 `8.5`：一份候选若只匹配产品仍可获得少量加分；另一份同时匹配产品、错误码和版本会获得更多加分，但总增益仍被截到 `0.20`。完全没有显式写出 `8.5` 的文档不会因此被删掉，它仍可凭语义、标题和正文证据进入前列。

不做硬过滤很重要。文档可能使用产品别名、只在附件/标题提及版本、适用于一整个版本族，或题目中的错误码出现在长日志却不是根因。硬过滤会把真正正确但未显式写出同一个特征的文档永久排除，形成难以发现的假阴性。

## 7. 摘录器为什么偏好短而聚焦的句子

Top-3 文档不能把全文塞进回答或给生成模型的上下文。当前摘录器每个命中默认约 360 个字符，流程是：

1. 将正文按行和中英文句号/问号/分号切成证据单元；
2. 计算每句覆盖了哪些问题词；错误码、版本等技术词权重更高；
3. 在预算内贪心选择能带来**新增问题词覆盖**的句子；
4. 如果新增覆盖、总覆盖相同，优先更短的句子；再考虑出现次数和原文位置；
5. 若预算允许，补一条相邻句，以保留“条件 + 操作”这类不重复关键词的必要上下文。

因此“URL 很长”“参见文档”这类句子即使碰巧含一个关键词，也不应消耗大部分预算；它们通常不能直接回答问题。目标不是文本摘要，而是在很小预算中选出**可核验、能回答问题的证据句**。若没有任何问题词命中，才退回取正文开头。

例如两句都覆盖 `SQLCODE=-1585` 时，摘录器会优先选择“`SQLCODE=-1585` 表示临时表空间页大小不足”这类短而直接的因果句，而不是包含同一错误码、一个长 URL 和“详情参见……”的整段导航句。它优化的是有限回答预算里的**证据密度**，不是句子越短越好；必要的相邻操作句仍会被补入。

## 8. `replace` 与 `weighted_rrf`：这里的“weighted 重排”是什么

文中实际上有两层 RRF，名称相似但职责不同：

1. **召回层 RRF**：合并 dense、BM25、标题 BM25 等多个召回分支；
2. **重排融合层 weighted RRF**：合并“基础检索排名”和“LLM 给出的文档排名”。

本节说的是第 2 种。对于候选文档 `d`，代码使用：

```text
score(d) = (1 - w) / (k + base_rank(d))
         + w       / (k + llm_rank(d))

本实验：w = 0.5，k = 60
```

- `base_rank` 是进入 LLM 前的字段化 Hybrid 名次；
- `llm_rank` 是 DeepSeek 根据“能否直接回答问题”重新给出的名次；
- RRF 用名次而非不同检索器不可直接比较的原始分数，靠 `1/(k+rank)` 累加；
- `w=0.5` 表示基础排序和 LLM 各投一半票；较高的 `w` 会更信任 LLM。

`replace` 则不融合：**完全采用 LLM 名次**。它并不生成新候选，只重新排列同一批 20 份候选文档。

这是字段化检索阶段的一次严格 A/B；这批实验的基础名次较弱：无重排原生结果仅 Recall@3 `37/55`、Top-1 `24/55`。当 DeepSeek 已把正确文档排到前面时，`w=0.5` 又会把原先基础排名较差的正确文档往后拉。严格复用同一批 DeepSeek 判断后：

| 策略 | Recall@3 | Top-1 |
|---|---:|---:|
| `replace` | 46/55 | 40/55 |
| `weighted_rrf`，`w=0.5`、`k=60` | 42/55 | 28/55 |

这只说明**当前候选、模型和 0.5 权重**下，完全信任 DeepSeek 更好；不说明 RRF 本身错误。若要继续研究，应该冻结同一候选与同一模型判断，再扫描更高 LLM 权重（如 0.7/0.8/0.9），而不能用两次有随机漂移的在线模型调用比较。

## 9. dense、综合 BM25、标题 BM25、feature BM25 是召回，不是重排

你的判断是对的：这四路是**召回层**，负责扩大并补全候选池；重排在它们之后，比较已聚合成的 20 份不同文档。

| 召回分支 | 索引内容 | 问题侧输入 | 擅长解决的情况 |
|---|---|---|---|
| dense | `title + child content` 的语义向量 | 原问题与确定性聚焦问题，各做一次向量查询 | 同义表达、描述方式不同但语义相近。 |
| 综合 BM25 | `document_id + title + content` | 原问题与聚焦问题，各做一次词法查询 | 原词、编号、标题和正文混合匹配。 |
| 标题 BM25 | `document_id + title` | 聚焦问题 | 题目本身接近 IBM 文档标题时，避免长正文的常见词淹没标题。 |
| 显式 feature BM25 | 结构化 token，如 `product_*`、`component_*`、`identifier_*`、`version_*` | 从原问题抽取的特征 token | 错误码、版本、产品/组件等适合词面精确匹配的信息。 |

“聚焦问题”不是另一个会自由发挥的 LLM 改写：它保留原问题，同时从首行/主题和可识别的产品、组件、标识符、版本组合出一个确定性短查询。保留原问题是为了避免聚焦过程误删上下文。

这里说的“四路”是四种**召回信号类型**，不一定只有四个物理请求。当前原问题与聚焦问题会分别触发 dense 和综合 BM25，因此一次查询最多可形成 2 路 dense、2 路综合 BM25、1 路标题 BM25 和 1 路 feature BM25，共 6 个 `AnnSearchRequest`。

所有分支带相同的 `status + tenant + role` 过滤。Milvus 原生 `hybrid_search` 先取得各分支 Top-N，再用**召回层 RRF**合并候选；随后应用侧做特征小幅加分、按 `document_id` 聚合、补 parent，最后才可选 LLM 重排。两者分工如下：

```text
多路召回：尽量不要漏掉正确文档（Recall@20）
        ↓
文档级重排：把已经出现的正确文档推入 Top-3/Top-1
```

所以“Gold 不在 Top-20”是召回问题；“Gold 在 Top-20 却没进 Top-3”才是重排/基础排序问题。

## 10. 评测集究竟有多少题，各测什么

### 10.1 Gold 的演进

| 阶段/口径 | 总题数 | 分类与用途 |
|---|---:|---|
| P1 | 120 | `rag` 60（普通语义检索）、`exact_search` 20（编号/版本精确检索）、`tool` 20（只读 SQL/工具）、`unauthorized` 10（越权拒答）、`no_evidence` 10（无证据拒答）。 |
| P2 与历史 P3 正式规模评测 | 180 | 保留 P1 的 120；新增 `graph_rag` 40（目标、联合、路径）；新增 `graph_unauthorized` 20（图遍历不得泄露不可见节点）。 |
| P3 Gold 扩充后 | 240 | 普通 `rag` 从 60 增至 120；其余类别保持：exact 20、graph 40、graph unauthorized 20、tool 20、unauthorized 10、no evidence 10。新增 60 道普通 RAG 按 `engineering`、`operations`、`restricted` 各 20 道补齐。 |
| P3 Gold v4 逐题复核后 | 240 行，235 题计分 | 120 个 `rag` 中 5 个没有可靠证据链，保留记录但 `score_enabled=false`；因此普通 RAG 计分为 115，其他类别均计分。 |

“240 行”与“235 题计分”并不矛盾：被排除题仍留在 Gold 中，以便审计为什么不能把它当失败，而不是悄悄删除。

### 10.2 为什么报告中还会看到 80、55、40、20、105

一个报告只跑与问题相关的切片，分母因此不同：

| 报告里的 n | 对应题目 | 测的是什么 |
|---:|---|---|
| 180 | 历史 P2/P3 全量 Gold | 路由正确率、整体权限隔离等全链路指标。 |
| 80 | 历史 P3 的 `rag 60 + exact_search 20` | 基础检索 Recall@3 与 Top-1；不是 Graph 专项。 |
| 55 | 原始 60 道普通 `rag` 扣除后来确认无可靠证据链的 5 道 | 字段化检索、分块 × 模型消融、DeepSeek/Luna/Sol 重排，以及普通题强制 Graph 对照。它是历史小样本，不是扩充后 Gold 的正式发布基线。 |
| 40 | `graph_rag` | Graph 联合/目标 Recall 与路径准确率。 |
| 20 | `graph_unauthorized`，或 `tool`，或拒答类别中的一个切片 | 分别检查图 ACL、工具答案、拒答；必须看报告中的指标名确定是哪一类 20。 |
| 105 | 历史 P3 中“Gold 答案能装进摘录预算”的子集 | 长度可容纳答案片段命中率；答案本身长于证据预算的题不应用该门槛惩罚检索。 |
| 115 | 当前复核后可计分普通 `rag` | 扩充后应重测最终 Hybrid 策略的正式普通问答范围，复盘明确说明这项尚未完成。 |
| 135 | 当前复核后基础检索 `rag 115 + exact_search 20` | 扩充后可计分的基础检索总范围。 |

因此看到 `49/55`、`46/55`、`40/40`、`65% (n=80)` 时，先问四件事：**哪一份 Gold SHA、哪些类别、是否计分、是否启用重排/Graph**。它们回答的是不同问题，不能排列成一条“系统分数持续上升”的曲线。

## 11. 读复盘时可用的判断框架

1. 先看正确文档是否进入 Top-20：没进入，优先改召回、分块、字段或查询；
2. 再看它是否被排进 Top-3/Top-1：已进入却失败，优先查文档级表示和重排；
3. Graph 题同时看目标、联合和路径：目标命中不等于路径可审计；
4. 普通单文档题不要因为“Graph 专项 100%”就无条件扩图：当前固定插槽融合会挤占 Top-3；
5. 所有数字必须带上语料、chunk 契约、Gold SHA、候选数、模型判断缓存和检索模式，才可比较。
