# P3 NowCoding 重排评测与归因

## 结论

NowCoding Top20 文档级重排有明确正收益，但当前不应设为默认线上配置。

- 语义 RAG Recall@3 从 38/55（69.09%）提升到 46/55（83.64%），增加 8 个净命中，仍低于 85% 门槛。
- Top-1 从 32/55（58.18%）提升到 37/55（67.27%），增加 5 个净命中，距离 95% 门槛仍很远。
- 55 次正式重排调用全部成功，`degraded_calls=0`，提升不是接口降级或静默回退造成的假象。
- P50/P95 延迟分别增至 8.45 秒和 13.06 秒，约为无重排基线的 11.95 倍和 11.62 倍。
- 修复证据句选择后，短金标答案命中从 12/40（30.00%）提升到 14/40（35.00%），但仍低于 55% 回归门槛。

因此最终 `passed=false`。LLM 重排解决了一部分排序问题，但候选生成、排序稳定性、答案证据选择和延迟仍是独立瓶颈。

## 同口径结果

两组均只评测 55 条 `rag` 样本，使用相同的 Nemotron 1024、Milvus 索引、dense weight 0.7、search multiplier 30、Top3、抽取式答案和 curated gold。唯一检索差异是是否启用 NowCoding Top20 重排。

| 指标 | 无重排基线 | NowCoding | 变化 |
|---|---:|---:|---:|
| Semantic RAG Recall@3 | 69.09% | 83.64% | +14.55 个百分点 |
| Semantic RAG Top-1 | 58.18% | 67.27% | +9.09 个百分点 |
| Fitting answer hit | 30.00% | 35.00% | +5.00 个百分点 |
| Mean answer content recall | 0.4344 | 0.4535 | +0.0191 |
| MRR@3 | 0.6273 | 0.7424 | +0.1151 |
| nDCG@3 | 0.6365 | 0.7476 | +0.1111 |
| P50 latency | 707.34 ms | 8452.48 ms | +7745.14 ms |
| P95 latency | 1123.93 ms | 13063.83 ms | +11939.90 ms |

NowCoding 的 Recall@3 95% 置信区间为 71.74%-91.14%，Top-1 为 54.10%-78.19%，短答案命中为 22.13%-50.49%。三项的区间下界均未达到门槛。

## 逐题归因

重排新增 Recall@3 命中的 9 题：`rag-001`、`rag-009`、`rag-023`、`rag-026`、`rag-028`、`rag-031`、`rag-033`、`rag-039`、`rag-051`。

重排造成 Recall@3 回退的 1 题：`rag-035`。其金标文档在无重排结果中可命中，但被纯 LLM 顺序替换挤出 Top3，说明当前“完全采用 LLM 名次”的策略缺少基线保护。

仍未进入 Top3 的 9 题：`rag-002`、`rag-012`、`rag-029`、`rag-034`、`rag-035`、`rag-045`、`rag-046`、`rag-056`、`rag-059`。

这些失败主要分成三类：

1. 查询与金标标题/正文表达错位。例：`rag-059` 问 TLS 1.2 配置，但答案埋在 DataPower Agent fix pack 的长发布说明中；`rag-029` 问产品兼容性，金标是 fix pack 文档。
2. 长问题中的日志和通用错误词稀释核心意图。例：`rag-002` 同时包含 BPM 迁移、MQ 2035、用户名和长堆栈；`rag-034` 的关键现象是远程 JMS 3 秒等待，但金标标题是通用总线连接异常。
3. 纯列表式排序不稳定。相对无重排基线，Top-1 修复 7 题但回退 2 题（`rag-005`、`rag-044`）；两次 NowCoding 专项运行的 Recall/Top-1 也各有 1 题波动，即使温度为 0，托管端点仍不能视为完全确定性排序器。

答案侧也不是单纯的检索问题。抽查发现，正确文档已排第一时，旧摘录器仍会让包含 URL 的长“参见文档”句凭重复词频占满 360 字预算，漏掉更短的真正答案句。现已改为同等查询词覆盖下优先更短、更聚焦的证据句；此外，受限文档 ID 改为精确 token 替换，不再删除授权文档的整行公开文本。该修复在无重排基线上将 fitting answer hit 从 11/40 提升到 12/40，最终组合达到 14/40。

## 已实施修复

- 评测与服务共用组件 factory，避免离线/线上配置漂移。
- 增加 `reranker_stats.calls/degraded_calls/degraded_rate`，接口失败不再被静默伪装成模型结果。
- 增加 `--category` 专项评测和按范围动态质量门槛，避免为了评估语义重排重复调用图、工具和精确检索路径。
- 报告保存全部逐题结果，后续归因无需再次调用外部模型。
- 证据摘录在相同词覆盖下优先短而聚焦的句子。
- ACL 脱敏只替换精确受限文档 ID token，保留同一行中的授权公开内容；API ACL 回归测试保持通过。

## 后续修复优先级

1. 候选生成：从长问题提取“产品 + 组件 + 错误码/版本 + 核心动作”的短查询，与原问题并行检索，再按文档做 RRF 合并。重点覆盖 fix pack、发布说明和标题不直接描述答案的文档。
2. 字段化召回：标题、产品、组件、错误码、版本和正文分别建权重；错误码与版本走精确 token 分支，不再只依赖正文 BM25/向量相似度。
3. 排序融合：不要完全替换基础排序。评测 base rank 与 LLM rank 的加权/RRF 融合，并对 `rag-035`、`rag-005`、`rag-044` 设置回归保护。
4. 真实候选追踪：在一次检索调用内记录送给 reranker 的实际 20 个文档。当前另跑 `top_k=20` 会改变原始池大小，不能作为严格的线上候选上限。
5. 答案结构：识别 FAQ 的 `ANSWER`、Technote 的 `RESOLVING THE PROBLEM`、版本表和配置键值，优先从答案区选句；继续用 fitting gold 和人工相关性复核约束回归。
6. 延迟：在质量回归集上比较 8/12/20 候选窗口；加入有界缓存和超时预算。P95 约 13 秒时不应默认启用同步重排。
7. 训练数据：人工复核 `p3-repaired-hard-negative-review.jsonl` 后，再按文档/产品分组切分训练与测试，训练领域 cross-encoder；不得把未复核非金标候选直接当负例。
